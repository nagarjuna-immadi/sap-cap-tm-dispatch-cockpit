# Phase 6: Agents and MCP servers

[← Development plan](README.md) · Previous: [Phase 5](phase-5-extras.md)

**Goal:** a dispatcher and a carrier desk user can run the tender flow by chatting with an agent. Each agent runs on top of the existing services, under the user's own roles, and every write needs the user's explicit approval. The same capabilities are also offered as MCP servers, locally and on BTP, where external MCP clients (Claude Code, claude.ai, VS Code) log in as the BTP user. Everything runs on BTP trial **without AI Core or Joule** (blueprint §13).

This phase does not depend on phase 5. It can be built before or after it.

## Approach in short

| Concern | Choice | Why |
| --- | --- | --- |
| MCP server | [`@cap-js/mcp`](https://cap.cloud.sap/docs/guides/protocols/mcp) (official CAP plugin, protocol `mcp` at `/mcp/<service>`) | A service becomes an MCP server by adding a protocol annotation. `@requires` and `@restrict` are enforced per user, and the tools are `describe`, `query`, `call` and optionally one tool per action. |
| Agent | [`@cap-js/agents`](https://cap.cloud.sap/docs/guides/ai/cap-agents) (official CAP plugin, `@agent`, A2A at `/a2a/<service>`) | LangGraph-based, uses the service's own MCP tools, has human-in-the-loop via `@agent.hitl`, persists conversations in the app DB, and has quotas. Node.js only, which fits this project. |
| LLM without AI Core | `cds.requires.llm.kind: "anthropic"`, which calls the Anthropic API directly with an API key | The plugin ships an `anthropic` model adapter next to `aicore` and `mock`. It reads `apiKey`/`anthropicApiUrl` from the credentials or from `ANTHROPIC_API_KEY`. The key is billed per use, so quotas are set. |
| Chat UI (local) | The plugin's chat preview at `/a2a/<service>/preview/`, plus Claude Code (or OpenCode) as the MCP client, registered automatically by the plugin's autowire | Needs no UI code, so the agents can be tuned before the UI exists. |
| MCP in the cloud | External clients call `/mcp/<service>` on the `-srv` route directly with an XSUAA user token (authorization code + PKCE, a fixed client from the app's own XSUAA instance). The app publishes OAuth protected-resource metadata so clients can discover the login. | XSUAA has no dynamic client registration, and trial has no IAS in the setup. A fixed client needs no new service, and the token carries the user's role collections, so `@requires`/`@restrict` apply as in the UIs. |
| Chat UI (cloud) | New UI5 freestyle app **TM Assistant** (`app/assistant/`) in the Work Zone site, which calls A2A through the approuter | The preview is a dev tool. A launchpad app reuses XSUAA login, role collections and the existing Work Zone setup. |

## 6.0 Decisions and prerequisites

- [x] **LLM account:** create an Anthropic API key (console.anthropic.com) and set a monthly spend limit there. Pick the models: `claude-haiku-4-5-20251001` for development (cheap) and `claude-sonnet-5-5` for the cloud.
- [x] **SAP API Policy (open decision 4):** the CAP agents docs say agents are for *custom* CAP services, **not** a path for agentic access to SAP application APIs (SAP API Policy §2.2.2). `DispatchService.FreightOrders` is a projection straight onto `CE_FREIGHTORDER_0001`. So the agent services below expose **no generic TM entity**: they expose local tender data plus a small, fixed freight order context (ID, lane, dates, dispatch status). Confirm this boundary before building. It also matches "TM is read-only" (§1). §2.2.2 does not say how far removed from the API an agent must be, and an agent tool that triggers a TM read is still a gray area. So also pick the source of the freight order context: (a) a live TM read in our code with a fixed `$select`, where LLM input never reaches `$filter`/`$expand`, or (b) the strictest reading, a local snapshot of those few fields on `FreightOrderDispatch` (written when a tender starts), so agent tool calls trigger no TM call at all.
- [x] **Trial quota:** the plugin docs suggest 1024M for the CAP module (LangGraph and the MCP SDK). Checked with `cf org-quota` and `cf apps`: the org quota is 4G, and only `-srv` (256M) and the approuter (256M) run; stopped apps (`-db-deployer`, `incident-management-*`) do not count. **Decision: raise `-srv` to 1024M** in 6.6. That gives 1280M running plus staging headroom during `cf deploy`, and still over 2G free.

## 6.2 `DispatchAgentService` (Dispatcher)

The existing services are shaped for Fiori (drafts, virtual columns, TM projections, a READ handler that maps OData query options). So the agents get **their own narrow services** that delegate to the existing ones. Rules stay in `award-rules.js` and `DispatchService`, and nothing is implemented twice.

- [x] `srv/agents/dispatch/dispatch-agent-service.cds` / `.js` (one folder per agent, holding the service, its handler and the persona): `@path: 'dispatch-agent'`, `@requires: 'Dispatcher'`, `@protocol: ['mcp', 'agent']`, `@agent.connect: 'none'`, plus `@mcp.instructions`. CAP loads only the `.cds` files directly in `srv/`, so `srv/agents.cds` pulls the agent services in with a `using from` line each (as `app/services.cds` does for the annotations). The handler imports the shared helpers from `../../lib/`. Every element and action gets a `/** doc comment */`, because it becomes the tool description the LLM reads. The service's own doc comment goes into the agent's system prompt, the agent card and the MCP server description.
  - `@protocol` must list **both** protocols. Once `@protocol` is set, CAP ignores the `@agent` / `@mcp` shorthands, so `@protocol: ['mcp']` plus `@agent` would serve MCP only.
  - `@path` has **no leading slash**. With one, CAP uses the path as it is for every protocol, and both adapters would be mounted at `/dispatch-agent` instead of `/mcp/dispatch-agent` and `/a2a/dispatch-agent`.
  - `@agent.connect: 'none'`: the plugin default (`auto`) gives an agent the tools of every other MCP or agent service in the model, which would add the tender agent to the dispatch agent after 6.3.
  - Checked on a local server: `/mcp/dispatch-agent` answers `initialize` for `nag` with the custom instructions, 403 for `satish` and 401 without a user; `/a2a/dispatch-agent/.well-known/agent-card.json` is 200 for `nag` and 403 for `satish`. The service is empty until the next steps, so `tools/list` returns nothing yet.
- [x] Read-only projections for the `query` tool, local DB only: `Dispatches`, `TenderRounds`, `CarrierOffers` (with carrier name, price, transit, status), `Carriers`, `ExecutionEvents`.
  - Explicit columns, no handler code (the generic handlers read the DB). Code list associations are flattened to their codes (`status`, `mode`, `eventType`, `delayReason`, `currency`), and the doc comments name the values, because the code lists and `DispatchNotes` are not exposed. `freightOrderId` is on every entity, so a question about one freight order needs no join; the associations (`rounds`, `offers`, `dispatch`, `round`, `exceptions`) still work for nested reads.
  - Expiry is evaluated on read in the projections, with the rules of `award-rules.js` / `enrich.js`: `CarrierOffers.status` reads `EXPIRED` for an `INVITED` offer past the round deadline, and `TenderRounds.deadlineExpired` is true for an open round past its deadline. Both can be filtered on.
  - `Carriers` lists active carriers only, the same set `startTender` accepts.
  - Checked on a local server as `nag`: `tools/list` shows `DispatchAgentService-describe` and `-query`; `describe` returns the doc comments per element; nested, filtered and aggregate queries return the rounds and offers created through `DispatchService` / `TenderService`; `DispatchNotes` is rejected as not resolvable.
- [x] Functions that bring in the TM context through `DispatchService` (`cds.connect.to('DispatchService')`, run in the caller's `cds.context`, so the user and roles carry over):
  - `openFreightOrders(lane: String, status: String, top: Integer)`: compact rows (ID, lane, pickup and delivery, dispatch status, best quote, quote count, deadline).
  - `freightOrderSummary(freightOrderId)`: header, lane, dates, freight unit count, rounds and offers.
  - `compareOffers(freightOrderId)`: offers of the open round ranked by price and transit time, with `canAward` and the rule message from `award-rules.js`, so the agent can explain *why* an offer cannot be awarded yet.
  - **No parameter reaches the TM `$filter`** (decision 6.0, option a). `status` is checked against the `DispatchStatus` code list and resolved locally by the existing `local-filter.js` path. `lane` is matched in memory on the rows TM returned (`'MUC -> VIE'`, `'MUC ->'`, `'-> VIE'` or a single term for either end; substring of the location ID, ignoring case). `top` is clamped to 1–50 (default 20).
  - A lane filter cannot be paged in TM (the lane is on the stops), so with a lane the function reads up to 500 unassigned freight orders and filters them. `total` then counts the matches among those 500. Without a lane, `total` is TM's `$count`. Fine for the mock data and the sandbox; on a tenant with more open freight orders the lane would need a local snapshot (decision 6.0, option b).
  - The functions only read. `freightOrderSummary` uses the list read with a key filter, not the single read, which would create the dispatch of the freight order as a side effect of a question.
  - Rounds and offers come from this service's own projections, so the functions show the same values as the `query` tool (offer status with expiry applied). `compareOffers` falls back to the last round when none is open (after an award it shows `WON`/`LOST`), and it leaves `rank` empty with a `note` when the quotes are in different currencies, as `bestQuote` does.
  - The return shapes are named types in the service (`FreightOrderList`, `FreightOrderSummary`, `OfferComparison`). With `per_action_tool`, the plugin appends them to each tool description.
  - Do not name a service field `this.dispatch`: it replaces the method every CAP service dispatches its requests with, and then every call on the service fails, the `query` tool included. The connection is `this.dispatchService`.
  - Checked over MCP on a local mocked server as `nag`: list, status filter, the lane variants, an unknown status and a malformed lane (400 with the valid values), summary of an order with and without a tender (the latter creates no dispatch), comparison in a PEER round, in a BROADCAST round before the deadline (`canAward` false with "award only after the quote deadline has passed") and after it, and with mixed currencies. `satish` gets 403.
- [x] Actions with `@agent.hitl` (the task pauses in `input-required` until the user approves) that delegate to the existing bound actions: `startTender(freightOrderId, mode, deadline, carriers)`, `cancelTender(freightOrderId, reason)`, `closeRound(freightOrderId)`, `award(offerId)`, `reportException(freightOrderId, type, reason, minutes)`.
  - A bound action is called from code with `dispatchService.send({ event, target, params: [key], data })`. `startTender` / `cancelTender` take `{ TransportationOrder }` (and create the dispatch, as in the cockpit). `closeRound` / `reportException` are bound to `Dispatch`, so the handler looks up the dispatch ID by freight order ID and passes `{ ID, IsActiveEntity: true }`; `award` passes the offer ID the same way. No rule is checked in the agent service: a violation comes back with the message of `award-rules.js` / `DispatchService`.
  - Every action returns the `FreightOrderSummary`, so the agent sees the result (new round, award, status) without a second call. The action and its summary read share one transaction: if the summary read fails, the change is rolled back.
  - The plugin pauses a tool when `srv.actions[<tool name>]['@agent.hitl']` is set, and the agent's own tools are named without the MCP prefix, so the five actions match. The functions are not paused. (Without a persona folder the agent card lists each action with a `hitl` tag; with the persona below, the card lists the persona's skills instead.)
  - **Validation messages:** CAP's input validation errors (`@mandatory` on a blank string, a wrong type such as `deadline: "tomorrow"`) carry only a code; the text is added in the OData error response. Over MCP and A2A the LLM would get `undefined`. An `on('error')` handler in the agent service resolves the text and adds the parameter name ("Value tomorrow noon is not a valid Timestamp (deadline)"). `TenderAgentService` (6.3) needs the same handler.
  - Checked over MCP on a local mocked server as `nag`: start (PEER and BROADCAST), the rejections (open round, deadline in the past, unknown mode, unknown carrier, no carrier, unknown freight order, no round to close, unquoted or unknown offer, second award, delay without reason), award after a quote from `satish` (`awardedBy` is `nag`, also in the cockpit's view), close round, cancel (`FAILED`), report a delay (`reportedBy` is `nag`). `satish` gets 403.
  - Not run yet: the pause and approval itself, which needs a chat with the LLM (billed). It is part of the 6.4 scenario in the chat preview.
- [x] Verify that `DispatchService`'s `FreightOrders` READ handler also works when called with a CQN `SELECT` from code, not only from OData. If it only reads OData query options, give `tm-client` a small CQN entry point instead of copying the logic.
  - It does: the handler reads `req.query.SELECT` (where, orderBy, limit, count), so `dispatchService.run(SELECT.from(FreightOrders)…)` works with a filter on `dispatchStatus`, with `orderBy`, `limit` and `count`, and so does `FreightUnits` with `where freightOrderId = …`. No change to `DispatchService` or `tm-client` was needed.
  - A `SELECT` from code always takes the **list** path: `req.params` is empty unless the key is in the path, so a `where TransportationOrder = …` does not trigger the single read (and its lazy dispatch creation). The write actions in the next step are bound and go through the single-order path, which creates the dispatch.
- [x] Persona: `srv/agents/dispatch/AGENTS.md` (role, tone, "always name the freight order ID", "never guess prices; read them", "state the deadline in UTC and the user's time") plus skills `skills/tendering/SKILL.md` and `skills/award/SKILL.md` (BROADCAST vs. DIRECT, award preconditions, when to close a round). The plugin looks for this folder relative to the service's `.cds` file: `@agent.directory` first, then by convention `AGENTS.md` next to it, then `dispatch-agent/`, then `agents/dispatch/`. The service file is in `srv/agents/dispatch/` next to `AGENTS.md`, so the first convention matches and no `@agent.directory` is needed. If the two are separated nothing fails: the plugin silently builds the plain agent without the persona. For the same reason each agent needs its own folder: two services next to one `AGENTS.md` would both pick it up.
  - **What the folder changes:** with an `AGENTS.md` the plugin builds a *deep agent* (`deepagents`): `AGENTS.md` is loaded into the prompt on every turn, and each `skills/<name>/SKILL.md` is listed by the `name` and `description` of its frontmatter and read by the agent when it needs it. So the description must say when to read the skill, and `name` must equal the folder name. The HITL middleware applies as before.
  - **Agent card:** with the folder, the A2A agent card is no longer generated from the CDS model. Name, description and version come from the frontmatter of `AGENTS.md` ("TM Dispatch Assistant"), and the card's skills from the `SKILL.md` frontmatter (`metadata.tags`, `metadata.examples`). TM Assistant (6.5) can show these examples as suggestions.
  - **Modes:** the real modes are `BROADCAST`, `PEER` and `SPOT`, not "DIRECT". The only difference the app enforces is that a `BROADCAST` round can be awarded only after its deadline; the skill says so.
  - **Rules the skills spell out, taken from `award-rules.js` and `DispatchService`:** a round can be started only in `NEW` or `TENDERING` with no open round; an offer can be awarded only while its round is open, so closing a round with quoted offers loses them; `cancelTender` is final (`FAILED` allows no new round) and is accepted from any status, including `AWARDED`; an award cannot be undone; the time of an execution event is the time of the report.
  - **Time:** the agent has no clock, and the plugin's system prompt gives it none. The persona tells it to read the current time with the query tool (`SELECT $now as now from Carriers limit 1`, checked: returns the UTC timestamp) before it turns "in 2 minutes" into a deadline. The user's local time is given only once the user has named their time zone; the agent cannot know it otherwise.
  - Checked on a local server with the mock LLM (`CDS_CONFIG` override, no API call): the log shows the deep agent built from `srv/agents/dispatch`, the agent card shows the persona name and both skills with their examples, and an A2A `message/send` as `nag` completes a task. How well the persona steers the real model is part of the 6.4 scenario.

## 6.7 MCP servers on BTP for external clients

Required (the user's decision). External MCP clients reach the two MCP servers in the cloud and log in as the BTP user, so the same roles apply as in the Fiori apps.

**Decided approach:** the clients call the **`-srv` route directly** (`https://<srv-host>/mcp/dispatch-agent`, `/mcp/tender-agent`), not the approuter. The approuter works with session cookies, while MCP clients send `Authorization: Bearer <JWT>`, which CAP validates itself. The token comes from the app's **own XSUAA instance** through authorization code + PKCE, using a fixed client (a service key), because XSUAA offers no dynamic client registration. IAS stays the fallback only if a target client cannot be configured with a fixed client ID.

- [ ] **Checks before building** (they decide the details):
  - `@cap-js/mcp` 1.5.0 answers an unauthenticated call with a plain JSON 401 (`lib/index.js`), without `WWW-Authenticate: Bearer resource_metadata="…"`. MCP clients need that header (or the well-known URL) to discover the login, so the app adds it (next item).
  - Does XSUAA serve authorization server metadata that the clients read (`<xsuaa-url>/.well-known/oauth-authorization-server`, or `/.well-known/openid-configuration`)? Does it accept PKCE (`S256`) on the authorization code flow? If metadata is missing, the app serves an RFC 8414 document itself that points at the XSUAA `/oauth/authorize` and `/oauth/token` endpoints.
  - Which target clients accept a fixed client ID (and secret): Claude Code (`claude mcp add --transport http … --client-id … --client-secret`), claude.ai custom connector (advanced settings: OAuth client ID/secret), VS Code (asks for a client ID when registration fails). Start with **Claude Code**, then claude.ai.
